# Метрики оценки сервиса

Этот документ описывает, какими метриками EnergeticHack измеряет качество
собственной работы, как они считаются и где на них можно посмотреть
(`/metrics` в веб-интерфейсе, `app/metrics.py` в коде). Методика открыта и
воспроизводима: все числа считаются из данных, которые уже есть в БД
(статьи, дайджесты, фидбек), без скрытых допущений.

## Соответствие критериям заказчика

Организаторы хакатона (FAQ трека) назвали комплексную оценку дайджеста:
**полнота, точность, отсутствие дубликатов, скорость обнаружения,
доказуемость (ссылки на источник), экспертная полезность**. Ниже — как
каждая из них измеряется в сервисе.

| Критерий заказчика | Метрика в сервисе | Где считается |
|---|---|---|
| Полнота | охват по источникам и языкам (`source_category_coverage`, `language_coverage`), `considered_count` | `/metrics`, `compute_service_metrics` |
| Точность | `precision@10` по фидбеку пользователя | `compute_profile_metrics` |
| Отсутствие дубликатов | `duplicate_rate` = объединено дублей / всего рассмотрено | `stats["dedup_merged_count"]` из `build_digest` |
| Скорость обнаружения | `avg_selected_age_hours` — средний возраст отобранных материалов на момент генерации | `compute_profile_metrics` |
| Доказуемость | 100% пунктов дайджеста содержат ссылку на первоисточник — это инвариант рендера (`render_markdown`), а не опциональная метрика | `tests/test_markdown.py::test_every_item_has_a_source_link` |
| Экспертная полезность | не автоматизируется — оценивается людьми (судьи/пользователи) через фидбек 👍/👎 на карточках, что и подпитывает precision@10 | UI дайджеста |

## Метрики для оценки критериев самого хакатона

| Критерий хакатона (0–10) | Как сервис это показывает |
|---|---|
| Репрезентативность материалов | Страница «Источники»: количество подключённых источников, категории (vendor/media/government/community/research), статус здоровья каждого. Страница «Метрики»: языковой охват. |
| Качество и новизна технической реализации | Explainable-ранжирование («почему выбрано» на каждой карточке), гибридный BM25+feedback+recency+trust скоринг, дедуп (exact+fuzzy), TF-IDF-кластеризация тем, pluggable LLM-провайдеры с graceful fallback, сравнение профилей на одном срезе. |
| Бизнес-ориентированность | `estimated_minutes_saved` (оценка сэкономленного времени), раздельные аудитории technical/management, ролевые профили, страница сравнения профилей демонстрирует ценность персонализации. |

## Формулы

### `duplicate_rate`
```
dedup_merged_count = considered_count − number_of_dedup_groups
duplicate_rate = dedup_merged_count / considered_count
```
Считается в `app/digest/builder.py::SelectionResult.stats` на каждом прогоне
дайджеста.

### `precision@10`
Берутся первые 10 пунктов последнего дайджеста профиля. Для тех, что
получили фидбек (👍/👎 или рейтинг), считается доля положительных:
```
precision@10 = |{i ∈ top10 : фидбек(i) = релевантно}| / |{i ∈ top10 : есть фидбек}|
```
Без фидбека метрика не считается (`None`, отображается как «нет фидбека») —
это осознанное решение: подставлять 0 или 100% без данных было бы
некорректно.

### `avg_selected_age_hours`
Среднее `(generated_at − published_at)` по всем пунктам дайджеста, в часах.
Меньше — значит дайджест обнаруживает новости быстрее после публикации.

### `estimated_minutes_saved`
Грубая бизнес-оценка:
```
estimated_minutes_saved = considered_count × 3 мин − selected_count × 1 мин
```
Допущение: без сервиса аналитик тратит ~3 минуты на просмотр каждой
рассмотренной публикации, чтобы решить релевантна ли она; с сервисом —
~1 минуту на уже отобранный и суммаризированный пункт. Коэффициенты вынесены
в константы (`app/metrics.py: READ_MINUTES_PER_*`) и легко калибруются под
реальные данные организаторов.

## Golden-set: precision/recall независимо от живого фидбека

`precision@10` из `/metrics` честно показывает «нет фидбека», пока
никто не нажал 👍/👎 — у судей на демо фидбека обычно не будет. Поэтому
есть второй, независимый способ измерить точность ранжирования:
**вручную размеченный набор** `data/fixtures/golden_labels.json` — каждая
из 35 демо-публикаций помечена релевантна/нет для двух демо-профилей
(«SOC-аналитик» и «Platform/AppSec-инженер») **по смыслу темы**, а не по
совпадению ключевых слов с BM25-запросом — иначе проверка мерила бы
алгоритм его же собственной логикой.

```bash
python -m scripts.evaluate
```

Реальный результат на этом корпусе:

| Профиль | Размечено релевантных | precision@5 | recall@5 | precision@10 | recall@10 |
|---|---:|---:|---:|---:|---:|
| SOC-аналитик | 20 из 35 | 1.00 | 0.25 | 1.00 | 0.50 |
| Platform/AppSec-инженер | 13 из 35 | 0.80 | 0.31 | 0.80 | 0.62 |

Recall на небольшом K упирается в размер K относительно числа релевантных
статей в корпусе (это нормально и ожидаемо), а не в качество ранжирования —
отсюда он ниже precision; значение precision — то, что отвечает на вопрос
«сколько мусора в топе» — важнее при фиксированном малом K дайджеста.

## Что не автоматизировано и почему

- **Экспертная оценка полезности** — намеренно оставлена людям (через
  фидбек в UI), а не эмулируется LLM-судьёй: авто-оценка LLM своих же
  выборов была бы circular и не то, что просят организаторы.

## Как посмотреть

```bash
python -m scripts.run_demo --period daily   # сгенерировать дайджесты для всех демо-профилей
uvicorn app.main:app --port 8899            # затем открыть http://localhost:8899/metrics
```
